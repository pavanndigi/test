## 1. Bottom line

- **PdfCraft works as a PDF reader and editor on this test set.** All 15 files opened (one needed its password). Page 1 rendered within 1–2% of Poppler's ink. Text extraction found 100% of the expected strings on every born-digital file. Edits on all 14 files with a text layer saved to files that pass `qpdf --check` and reopen. The scanned page has no text to edit.
- **Its PDF→DOCX export is a baseline, not a reconstruction.** Measured problems:
  - Every font becomes Arial.
  - Columns collapse to one.
  - Vector art and transparent shapes disappear.
  - Headers and footers become body text.
  - A ruled table came out as a 7-column grid with one header cell pushed outside the table.
  - Invisible OCR text came out as visible text on top of the scan.
- **WordCraft's validator passed every export.** It skips the `mc:AlternateContent` wrappers where PdfCraft puts its text boxes. WordCraft's renderer honoured the text-box rotation that LibreOffice ignored.
- **OCR in a source build** runs only through an installed Tesseract. PdfCraft's built-in engine (ocrs) needs model files (CC-BY-SA-4.0) that a source build does not include.

## 6. Method

For each file the harness runs these steps:

1. **Open:** `pdfcraft-cli info`. File 15 is also tried without the password.
2. **Render:** page 1 at 100 dpi with `pdfcraft-cli render` and with `pdftoppm`. The two renders are compared by **SSIM** and by **ink F1**: pixels darker than 160 are counted as ink, matches allow 1 px tolerance, and F1 is the matched ink over all ink. Ink F1 was added because SSIM on mostly white pages mainly reflects anti-aliasing.
3. **Select text:** `pdfcraft-cli text` is compared with the ground truth. The script then runs `text_lines`, `text_paragraphs` and `page_images` through `pdfcraft-cli run --script … --report`.
4. **Edit:** `text_edit` replaces line 1 of page 1 with "EDITED BY TEST HARNESS".
5. **Save and reopen:** `doc_save` to a new path. The saved file is then reopened with `info`, checked with `qpdf --check`, searched for the new text with `pdftotext`, and rendered for comparison with the original.
6. **DOCX export:** `doc_export_office`. The harness inspects `word/document.xml`, `styles.xml` and `fontTable.xml`, converts the DOCX to PDF with LibreOffice, and scores page 1 against the original.
   - LibreOffice stands in for Word. It is **not** Word, so DOCX visual scores are a proxy.

The harness ran twice. The first run cut long JSON reports short, which wrongly suggested a word-count loss on file 14. The fixed second run is the one reported here. Additional targeted runs are in `extra/`, `ocr/` and `perf/`.

## 8. Observations by capability

### 8.1 Rendering — Observed

PdfCraft (Hayro + vello_cpu) matched Poppler closely on every page tested, including transparency, rotated text, embedded subset fonts and images. Ink F1 ranged from 0.980 to 1.000.

### 8.2 Text extraction and structure — Observed

- **Reading order:** correct on the two-column file. "Paragraph 1." through "Paragraph 14." appear in order in `pdfcraft-cli text`.
- **Diagonal text:** PdfCraft returned whole lines for the 45° and −30° text. Poppler's `pdftotext` returned them as fragments, so PdfCraft was better on this case.
- **Paragraph detection (`text_paragraphs`):** on page 1 of file 4, paragraphs 4+5 and 9+10 were merged, so 11 source paragraphs came back as 10. File 11's header was split into its left and right parts.
- **Line model:** `text_lines` can return a style run as a "line". On file 4, line 1 is just the bold run "Paragraph 1.", so paragraph 1 has 10 visual rows (`rows` in `text_paragraphs`) but 11 lines.

### 8.3 Editing — Observed

| Case | Result |
| --- | --- |
| Replace a whole line in a std-14 or embedded font | Applied in place, same font, other content untouched (files 1–3, 5–11, 13–15) |
| Replace a style run inside a mixed-style line (file 4, line 1) | The longer bold text pushed the rest of the visual line right, **overlapping column 2**. No reflow or collision check. |
| Replace a whole paragraph with longer text (`paragraph: 1`, `extra/04_para_edited.pdf`) | Rewrapped to the paragraph width, but it **overlapped the next paragraph** (later paragraphs did not move). The paragraph's first-run style (bold) was applied to all the new text. |
| Text whose glyphs exist in the embedded subset (file 3) | Kept `AAAAAA+DejaVuSans`; the subset was unchanged (103 glyphs before and after) |
| Text with characters outside WinAnsi (ğ, ż, Ω) in an embedded-font line | Switched to a generated **Type 3 "Inter-Regular"** font (`needs_type3`, `crates/edit/src/text/fallback.rs:35`). The edit succeeded but the font identity changed. |
| CJK text | **Refused** in a source build: "this text needs PdfCraft's Japanese fallback font, which this build doesn't include" |
| Incremental save in place (300-page file, page 200) | File grew by 1,199 bytes; `qpdf --check` passed; edit read back correctly |
| Save to a new path | Full rewrite; version header 1.3/1.4 → 1.5; encryption kept on file 15 |

### 8.4 DOCX export — Observed

- **Fonts:** one body font, Arial, in `styles.xml` and `fontTable.xml` for every file. This matches `crates/export/src/as_docx.rs:46`. Bold, italic and point sizes were kept per run.
- **Tables:** detected on files 5 and 6 and written as a `w:tbl`. The grid had 7 columns for 5 data columns, two of them empty spacers 400 twips (0.28") wide. The "Q3" header was emitted after the table. Table borders were all `nil` even for the ruled table. Header shading was dropped. Files 5 and 6 produced byte-identical `document.xml`.
- **Columns and paragraphs:** a single-column section. Each source paragraph became two DOCX paragraphs, split after its first line.
- **Positioned content:** rotated text and the scanned page were written as page-anchored `wps` text boxes (with VML fallbacks) and a `behindDoc` full-page image. Raster images on a digital page flowed inline at the correct physical size (4.17" and 3.13").
- **Vectors and transparency:** not exported (files 8 and 9).
- **Headers and footers:** not exported as header/footer parts.
- **Completeness:** no text was lost. Word counts matched on every born-digital file, including all 203,100 words of the 300-page file.

### 8.5 Invisible text — Observed (defect)

Mode-3 (invisible) text was exported as ordinary visible runs, with no `w:vanish` and no colour change, in a text box over the page image. In LibreOffice every scanned word appeared twice (file 13 page 2, and the OCR'd file 12 below).

### 8.6 OCR — Observed

| Engine | Status in this build | Result on file 12 |
| --- | --- | --- |
| ocrs (built in) | **Unavailable:** "the text recognition models are not installed" | — |
| Tesseract 5.3.4 (installed separately; PdfCraft drives it as an external process) | Available | 23 words, mean confidence 95.8, **CER 0.0** against ground truth, 6.0 s for open + words + recognise + save + export + editable copy |

- **Searchable mode:** keeps the image and adds invisible text. `pdftotext` then returns the full memo.
- **Editable mode:** writes a new PDF of visible Helvetica text at the recognised boxes. Word sizes jitter slightly from word to word, and the scan's serif face is not identified.
- **Attribution:** recognition quality here belongs to **Tesseract, not ArtCraft**. One clean synthetic page says nothing about OCR accuracy in general.

### Validation of PdfCraft's exports

`wordcraft-cli validate --json` ran on all 16 DOCX files: 15 exports plus the OCR'd file 12. Results are in `evidence/functional/wordcraft/wordcraft_results.json`.

- All 16 passed with **0 findings**.
- 58 checks ran on files without text boxes; 55 on files with them. Three checks were skipped on those files, and the report notes that the contents of `mc:AlternateContent` were skipped. PdfCraft wraps every text box in `mc:AlternateContent`, so **its positioned content is largely not validated**.

To test the validator itself, five files were deliberately broken (`evidence/functional/wordcraft/negative/`):

| Defect injected | Verdict (exit code) | Rule fired |
| --- | --- | --- |
| Malformed XML in `document.xml` | Fail (1) | `XML-MALFORMED` |
| Image relationship to a missing part | Fail (1) | `REL-DANGLING`, `REL-TYPED` |
| No `[Content_Types].xml` | Fail (1) | `PKG-NO-CONTENT-TYPES` |
| Duplicate `wp:docPr` ids inside `mc:AlternateContent` | **Pass (0)**, no finding | none (content skipped) |
| Paragraph style not defined | Pass (0) | `REF-STYLE` as a **Warning** |

Package and XML integrity are caught reliably. Drawing-level problems inside `mc:AlternateContent` are not caught.

### Rendering PdfCraft's exports

`wordcraft-cli convert export.docx out.pdf` succeeded on all 16 files (0.01–0.68 s each). Page counts matched LibreOffice's, and ink F1 against the original was similar.

| File | LibreOffice | WordCraft |
| --- | --- | --- |
| 03 embedded fonts | 0.40 | 0.40 |
| 04 two columns | 0.32 | 0.33 |
| 05 ruled table | 0.10 | 0.11 |
| 10 rotated text | 0.38 | 0.48 |
| 14 large file | 0.38 | 0.34 |

What this showed (images: `diagrams/h_visual/*_lo_vs_wordcraft.png`):

- **Rotation:** WordCraft rendered the text boxes rotated as the XML specifies; LibreOffice did not. WordCraft wrapped text inside three of the five boxes (cause not investigated).
- **Table defects:** both renderers show the same table problems (no borders, "Q3" below the table). These are exporter defects, not renderer artefacts.

## 12. Limitations of this validation

- **Synthetic corpus.** Clean, generated files flatter every tool. Real scans, broken files, Type 3 and CID fonts, RTL scripts, forms and signatures were not covered.
- **No Microsoft Word.** DOCX fidelity was judged by XML inspection and LibreOffice 24.2. The rotation result in particular may differ in Word.
- **GUI untested.** Only `pdfcraft-cli` and its automation tools (the same engine crates the GUI uses, per Report B) were exercised.
- **Narrow ground truth.** Ground truth is strings and structure, not per-glyph positions or font identities. Font identity was checked separately with `pdffonts`.
- **Single machine.** Timings come from a debug-profile build on 2 vCPUs.
